# Portfolio: keep it current and push it

## What the portfolio is

`PORTFOLIO.md` (repo root) tells the story of the work to an outside reader: the problem, the method, the tool that was built, what was found, what went wrong and how it was handled, and what is next.
It is regenerated by hand from the observation notebook (`../../docs/observations/`), never from memory. Images are in `docs/portfolio/img/` (real data only: no simulated screens passed off as results).

## Steps

1. Read `../../docs/observations/README.md` (status board), `05-comparison-feetech-vs-robonine.md` and the newest entries of `observation-log.md`.
2. Update PORTFOLIO.md: "Results so far" table and findings, "Status" and "Next steps"; keep the numbers identical to the notebook. Add a new section for a new tool version only if one was released.
3. `python tools/sync_observations.py` (copies `../../docs/observations` to `observations/`).
4. `python selfcheck.py` must print ALL PASSED if code changed.
5. Check what will be committed: `git status`. **Never commit** `data/`, `settings.json`, `desktop.ini`, `__pycache__`, `docs/robonine_docs/` (third-party PDF) or anything with personal details (emails, account names other than the public GitHub repo owner).
6. Commit with a message that starts with the version or area (`v1.10.1:`, `observations:`, `portfolio:`) and ends with the attribution line given by the session. One commit per logical change.
7. **Push only when the user asked** ("push" / "publish"): `git push origin main`. Report the commit hash and the result. If the push fails, show the error and stop; do not force-push.
8. Tell the user what is now on GitHub in one or two lines.

## Style

Plain, specific, evidence-linked. State limits (one servo, one lever). Prefer tables for results. No marketing words, no claims the data does not carry.
